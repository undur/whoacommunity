Launching from Eclipseas a Java application, not as a "WOApplication"

WOLips adds a WOApplication launch type to Eclipse. If your application is built with Maven, don't use it: launch it as an ordinary Java Application with one VM argument added. You get the classpath Maven would give you, a debugger that reads the right code, and no dependency on the launcher.

This has been the recommendation since a 2022 comment on WOLips issue 153, filed in 2021. Recipe first, reasons after, from the WOLips, m2e and Eclipse sources.

1. The recipe

Right-click the class with the main method, usually Application, and choose Run As → Java Application. Then open the configuration it created, under Run → Run Configurations…, and check three things on the Arguments tab:

  • VM arguments: -DNSProjectBundleEnabled=true. Enables project bundles: components and resources are read from project folders, so a saved template is live without a build. Wonder also takes it as development mode. wonder-slim sets it itself when it finds build.properties in the working directory; Wonder and plain WebObjects need it set. Copy over any VM arguments the old configuration had as well: WebObjects 5.4.3 on Java 17 or later, for example, fails at start-up with an IllegalAccessError in NSTimeZone without --add-exports java.base/sun.security.action=ALL-UNNAMED.
  • Program arguments: whatever you had on the launcher's WO tab, for example -WOPort 1200 -WOAutoOpenInBrowser false. Without a port, WebObjects picks a free one each time.
  • Working directory: with WOLips installed, ${working_dir_loc_WOLips:MyApp} follows the WOLips preferences: it resolves to the project folder when WOLips' Generate bundles preference is off, and otherwise to the built MyApp.woa under build/ (dist/ for Ant projects), failing with Could not find working dir until that bundle exists. Generate bundles is on out of the box. The easiest is to turn Generate bundles off and leave the field at Default, the project folder. That works with wonder-slim and Wonder 7.5-SNAPSHOT. Wonder 7.4 and earlier fail at start-up from Default, with a NullPointerException in ERXApplication$Loader.collectMainProps: Wonder 7.4 reads the application's Properties as soon as the last framework jar has loaded, before the main bundle exists, and then looks only in Contents/Resources under webobjects.user.dir, which defaults to the working directory. On those, leave the field at Default and add -Dwebobjects.user.dir pointing at a built bundle to the VM arguments: ${project_loc:MyApp}/build/MyApp.woa with Generate bundles on, or the target/MyApp.woa that mvn package builds. The bundle is read only for that first look: once the application's project bundle has loaded, Wonder reads Properties again from the project, and templates and resources still come from the project.

Save, run or debug.

JDK arguments. HotswapAgent arguments usually belong on the JDK definition, not on each launch configuration. See the development setup guide.

2. What the WOApplication launcher did for you

  • Arguments. It appended the list from the WOLips launch preferences: a few dozen -WO… settings plus -DNSProjectBundleEnabled=true, -DWOUserDirectory, -WOApplicationClassName and -DNSProjectSearchPath. None of them is needed. Most restate WebObjects' own defaults: caching and opening a browser are off unless switched on, and -WOIDE WOLips, which Wonder reads as development mode, is covered by NSProjectBundleEnabled. -WODebuggingEnabled only sets NSLog's debug level. Carry over only what you set on purpose, such as -WOPort. Three of WOLips' shipped defaults do make a difference. WebObjects takes the host of the URL it prints and opens from -WOAdaptorURL, not -WOHost, and WOLips' http://127.0.0.1/cgi-bin/WebObjects made that 127.0.0.1; without it you get localhost, a different host with its own cookies. -WOIncludeCommentsInResponse false kept template comments out of responses, where JavaWebObjects' default puts them. -WOLifebeatEnabled true sent lifebeats to a wotaskd on port 1085.
  • Tabs. WO becomes the plain program arguments box. Log wrote its debug groups as -DNSDebugGroups="(…)"; write it yourself. Browser opened the URL printed to the console in Eclipse's internal browser; -WOAutoOpenInBrowser true has WebObjects open your system browser.

Nothing else is lost. Rapid turnaround and templates read from the project are the frameworks' doing, not the launcher's.

3. Why: how Eclipse builds a launch classpath

The classpath Eclipse hands the JVM is computed by a classpath provider named in the launch configuration. The default provider walks the project's build path as the IDE sees it: output folder, libraries, containers, and every referenced project expanded the same way.

For a Maven project that's wrong, because the build path isn't the runtime classpath: the Maven Dependencies container holds everything the project can compile against, test scope included. So m2e has its own provider, which asks Maven instead: the resolved dependencies for the launched scope, exclusions applied, one version of each library. m2e installs it, with a matching source path provider for the debugger, on exactly three configuration types: Java Application, JUnit and TestNG (MavenRuntimeClasspathProvider, MavenLaunchConfigurationListener).

WOApplication isn't one of them, and WOLips names its own provider instead: its launch delegate writes its own WORuntimeClasspathProvider into every configuration it creates, and a launch that finds the attribute missing, or set to an older WOLips id, puts it back, cancels that launch and asks you to launch again. That provider resolves the build path exactly like Eclipse's default one, and with Generate bundles on also reorders the result into WOLips' own framework order. Maven's resolution never runs.

4. The three symptoms

Test scope on the runtime classpath. The container's test-scoped entries are marked as such, and Eclipse drops them only when the configuration says exclude test code. Eclipse sets that flag when it creates a Java Application configuration for a non-test main class; WOLips' shortcut doesn't. Workaround within the old launcher: the Exclude test code checkbox on the Classpath tab.

Exclusions ignored, two versions of a library. This happens when one of your own frameworks is open in the workspace. m2e then puts that project on the application's classpath instead of its jar, which is what you want: edit the framework, and the application sees the change. The WOApplication launcher, though, builds the classpath by following the application's build path, and when it reaches the framework project it keeps following: first the framework's classes, then everything on the framework's own build path, which includes the framework's own Maven Dependencies.

Those dependencies were resolved for the framework, from the framework's pom. Maven resolves each project on its own, so nothing there knows about the application's exclusions or the versions the application settled on, and Eclipse only drops entries that are the exact same path. So a library you excluded in the application comes back through the framework. A library the application resolved to commons-lang 3.3 while the framework resolved it to 3.2 is on the classpath twice, and only the order decides which one loads. Two workspace frameworks that disagree do the same to each other.

The Eclipse code is DefaultProjectClasspathEntry, which follows a referenced project's whole build path by default. m2e's provider avoids this: it adds the framework project's classes and skips its dependencies, since the application's own resolution already covers them.

With every dependency coming from a jar, you get the first symptom only. Open one framework in the workspace and you get all three.

Not what the build produces. Maven, and so the deployed application, uses Maven's resolution. The classpath you develop against has more on it, and a library that is there in Eclipse but not in the build turns up missing on the server.

5. Debugging

Source lookup is a second computation, by the configuration's source path provider. m2e's comes with its classpath provider, for the same three types. A WOApplication configuration gets Eclipse's default, which resolves the same build path, duplicates included, but without the reordering WOLips' classpath provider applies when Generate bundles is on.

The JVM loads a class from the first jar on the classpath that has it. The debugger opens the first jar on the lookup path that has it: attached source if there is one, otherwise Source not found. With one copy of a library those agree. With two copies and the two orders differing, which takes that reordering, the JVM runs one and the debugger shows the other: lines don't match, or Source not found although the running copy has sources. That's the mechanism the code supports, consistent with what people have seen, not a bug reproduced step by step.

6. Good to know

  • Existing configurations. Nothing to convert. Make a Java Application configuration, copy over your arguments, delete the WOApplication one.
  • A log4j warning. If your tests have a log4j.properties, the old launcher's test scope configured log4j 1 from it at start-up. Without it, log4j 1 prints No appenders could be found for logger once, before Wonder configures logging from your Properties, as the built application does. It's harmless. Don't silence it with -Dlog4j.configuration if log4j 2 is on the classpath: log4j 2 reads that property too, as a log4j 1 configuration, and without the log4j 1.2 bridge it then loses its own.
  • Entity Modeler loads your model's classes for SQL generation through the same WOLips classpath computation, from a throwaway WOApplication configuration that never sets exclude test code. Usually harmless, but if it picks up a surprising class, this is why.
  • Ant projects have no Maven resolution to miss. The WOApplication launcher is still the way to run them.
  • ng-objects applications are plain Java applications from the start. Nothing to set.
