Launching from Eclipseas a Java application, not as a "WOApplication"

WOLips adds a launch configuration type to Eclipse called WOApplication, and a Run As → WOApplication menu item to go with it. If your application is built with Maven, don't use it. Launch the application as an ordinary Java Application instead, with one VM argument added. Everything then works the way it should: the classpath is the one Maven would give you, debugging steps through the right code, and nothing depends on a plugin.

This has been the recommendation since 2022, when the problem was written up in WOLips issue 153. This guide gives the recipe first, and then the reasons, taken from the WOLips, m2e and Eclipse sources.

1. The recipe

In Eclipse, right-click the class with the main method, usually Application, and choose Run As → Java Application. Depending on the frameworks, the application may run fine right away, or it may not find its components and resources, since nothing has told it that it's running from a project folder. Either way, stop it and open the configuration that was just created, under Run → Run Configurations…, in the Java Application group. Three things to check, all on the Arguments tab:

  • VM arguments: -DNSProjectBundleEnabled=true. Tells the frameworks that the application is running from its project folder, so components and resources are read from there and a saved template is live without a build. The WOApplication launcher added this for you. wonder-slim turns it on itself when it finds the project's build.properties; Wonder and a plain WebObjects application need it set. Set it regardless, it costs nothing. (Wonder's master branch has learned to detect a Maven project the same way, but no release has that yet.)
  • Program arguments: whatever you used to put on the launcher's WO Arguments tab, written out, for example -WOPort 1200 -WOAutoOpenInBrowser false. A fixed port is the one most people want; without it WebObjects picks a free one each time. Leave out what you don't need, the defaults are fine.
  • Working directory: leave it at Default. For a Java Application launch, the default working directory is the project folder, which is exactly where the application expects to find build.properties and its resources. The 2022 instructions set it to ${working_dir_loc_WOLips:MyApp}, which for a Maven project resolves to the same folder, but depends on WOLips. If you want it explicit, ${workspace_loc:MyApp} does the same without the dependency.

Save, and run or debug it. The console shows the application's URL as usual, and with wonder-slim also a line saying that build.properties was found and development mode is on. Debugging uses the same configuration: Debug As → Java Application, or the bug button next to the run button.

That is the whole recipe. The resulting configuration, as Eclipse stores it, looks like this, and the two provider lines are the ones that matter, as explained below:

<launchConfiguration type="org.eclipse.jdt.launching.localJavaApplication">
    <stringAttribute key="org.eclipse.jdt.launching.MAIN_TYPE" value="myapp.Application"/>
    <stringAttribute key="org.eclipse.jdt.launching.PROJECT_ATTR" value="MyApp"/>
    <stringAttribute key="org.eclipse.jdt.launching.PROGRAM_ARGUMENTS" value="-WOPort 1200 -WOAutoOpenInBrowser false"/>
    <stringAttribute key="org.eclipse.jdt.launching.VM_ARGUMENTS" value="-DNSProjectBundleEnabled=true"/>
    <booleanAttribute key="org.eclipse.jdt.launching.ATTR_EXCLUDE_TEST_CODE" value="true"/>
    <stringAttribute key="org.eclipse.jdt.launching.CLASSPATH_PROVIDER" value="org.eclipse.m2e.launchconfig.classpathProvider"/>
    <stringAttribute key="org.eclipse.jdt.launching.SOURCE_PATH_PROVIDER" value="org.eclipse.m2e.launchconfig.sourcepathProvider"/>
</launchConfiguration>

JDK arguments go elsewhere. The arguments that make HotswapAgent redefine classes while the application runs belong on the JDK definition, not on each launch configuration. The development setup guide covers that, and a configuration made as above picks them up.

2. What the WOApplication launcher did for you

The WOApplication launcher is Eclipse's Java launcher with extras, and some of those extras are worth knowing about, so you can decide what to replace:

  • Arguments. It appended a few dozen -WO… arguments from the WOLips preferences, most of them WebObjects' own defaults restated, plus the ones that mattered: -DNSProjectBundleEnabled=true, the working directory as -DWOUserDirectory, the main class as -WOApplicationClassName, and an -DNSProjectSearchPath listing the parent folders and every framework project in the workspace. With project bundles on, the first is the only one you need, and the others fall out of the launch itself.
  • Tabs. The WO Arguments tab, where arguments were ticked on and off, becomes the plain Program arguments box. The Debug groups tab wrote -DNSDebugGroups=(…); write it yourself if you use it. The Browser tab opened the application's URL when the console showed it; -WOAutoOpenInBrowser true has WebObjects do that itself.
  • Console helpers. WOLips watches the console for a couple of exceptions, an unknown key in a binding or a malformed declaration, and opens the component's file at the offending line. That is attached to every Java console in Eclipse, not to the WOApplication launcher, so it keeps working.

Nothing else is lost. Rapid turnaround, templates read from the project, the debugger: all of that is the frameworks' doing, not the launcher's.

3. Why: how Eclipse builds a launch classpath

When Eclipse launches a Java program, the classpath it hands the JVM is computed by a classpath provider named in the launch configuration. The default one builds the classpath from the project's build path as the IDE sees it: the project's output folder, its libraries, its classpath containers, and every project it references, each expanded the same way. For an ordinary Java project that's fine.

For a Maven project it isn't, because the build path is not the runtime classpath. The Maven Dependencies container that m2e puts on the build path holds everything the project can compile against, test dependencies included. So m2e brings its own provider, which asks Maven for the classpath instead: the project's resolved dependencies for the scope being launched, with exclusions applied and each library at the one version Maven's mediation chose. m2e installs that provider on every launch configuration it recognises, together with a matching source path provider for the debugger. It recognises exactly three configuration types: Java Application, JUnit and TestNG. You can see the list in MavenRuntimeClasspathProvider, and the listener that does the installing in MavenLaunchConfigurationListener.

WOApplication is not one of the three, so m2e leaves those configurations alone. And WOLips wouldn't let it in anyway: its launch delegate writes its own provider, WORuntimeClasspathProvider, into every configuration it creates, and puts it back before each launch if it finds it missing. That provider, in WORuntimeClasspathProvider.java, is a thin subclass of Eclipse's default one. For a Maven project it does nothing of its own: it resolves every build path entry through Eclipse's standard resolution, which is the IDE's view described above. Maven's resolution never runs.

From that, the three things the issue reports follow directly.

4. The three symptoms

Test scope on the runtime classpath. The Maven Dependencies container always holds the test-scoped dependencies, marked as test entries. Eclipse drops marked entries from a launch only if the configuration says exclude test code. When you create a Java Application configuration, Eclipse sets that flag for you whenever the main class isn't in a test folder; WOLips' Run As → WOApplication creates its configuration without it. So JUnit, Mockito and whatever else your tests pull in are on the classpath of the running application. This one has a workaround inside the WOApplication launcher: the Classpath tab has an Exclude test code checkbox.

Exclusions ignored, and two versions of the same library. This happens when a framework of yours is open in the workspace as a project. m2e then puts the project itself into the application's Maven Dependencies container, in place of its jar, and Eclipse's standard resolution expands a referenced project the way it expands the launched one: its output folder, and its whole build path, including its Maven Dependencies container. That container is the framework's own Maven resolution, done from the framework's pom, with no knowledge of the application's exclusions or of the versions the application's own resolution settled on. The application's container has the right answer, and the framework's resolution is spliced into it, at the position where the framework sits, with only exact duplicates dropped: a library you excluded is back, and a library you pinned is there twice, at two versions, the framework's older one possibly ahead of yours. Which one the JVM loads is a matter of classpath order. The code is in Eclipse's DefaultProjectClasspathEntry, which by default includes a referenced project's non-exported entries too. m2e's provider knows better: for a project found in the container it adds the project's classes and skips the project's Maven Dependencies container, since the application's own resolution already covers what the project depends on.

If every dependency comes from a jar in your local repository, with no framework open as a project, you get only the first symptom. Open one framework in the workspace, and you get all three.

Not what the build produces. Maven's own build, and so the deployed application, uses Maven's resolution. The classpath you develop and debug against is a different one, with more on it. A library that is there in Eclipse and absent on the server is the kind of bug this produces, and it's found on the server.

5. Debugging

The debugger finds source code through a second computation, the source lookup path, built by the configuration's source path provider. m2e's goes in alongside its classpath provider, for the same three configuration types. A WOApplication configuration gets neither, so its source lookup uses Eclipse's default, which mirrors the classpath above, with the same two versions of a library in it.

The JVM loads a class from the first jar on the classpath that has it. The debugger, asked for that class's source, walks the lookup path and shows the first source it finds, which is the first jar with a source attachment, not necessarily the jar the class came from. With one version of a library on the path, those agree. With two, they can disagree: when the copy the JVM loaded has no sources attached and the other one does, you step through the other version's code, and lines stop matching what executes; when neither has sources, you get Source not found for a library whose sources you thought you had. That's the mechanism the code supports, and it fits what people have seen; it is not a bug anyone has reproduced step by step. With one version of everything on the classpath, which is what a Java Application launch gives you, there's nothing to disagree about.

6. Good to know

  • Swapping only the provider doesn't work. Pointing a WOApplication configuration at m2e's classpath provider was tried first, in the issue. The classpath came out right, but the application failed to find some of its own classes, Main and DirectAction among them. The cause wasn't chased down, because a Java Application launch simply works.
  • Existing configurations. There's nothing to convert. Create a Java Application configuration as above, copy over any arguments you had, and delete the WOApplication one.
  • The same classpath elsewhere. Entity Modeler's SQL generation loads your model's classes through the same WOLips classpath computation. It's usually harmless there, but if SQL generation ever picks up a surprising class, this is why.
  • Ant projects. Everything above is about Maven projects. A WOLips project built with Ant, with its dependencies declared in the WOLips classpath containers, has no Maven resolution to miss, and the WOApplication launcher is still the way to run it.
  • ng-objects applications are plain Java applications from the start: a main method and a Maven classpath, nothing to set.
