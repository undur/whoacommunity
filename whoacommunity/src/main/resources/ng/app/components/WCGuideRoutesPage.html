URL routing in wonder-slimclean URLs, one table, same everywhere

A WebObjects application's URLs are usually long and opaque, like /cgi-bin/WebObjects/MyApp.woa/wo/3.0.1.2.

wonder-slim adds a route table, so an application can answer /shops/, /company/acme or /laws/2026/12/3 with whatever code you like: a page, a JSON document, a redirect. The same routes, written once, serve http://localhost:1200/shops/ during development and https://www.example.com/shops/ in production. This guide shows the API and the shapes it takes in real applications.

1. The route table

Routes are registered at startup, in the Application constructor or in a small class it calls. Each entry maps a path pattern to a handler:

import er.extensions.routes.RouteTable;

public Application() {
    final RouteTable routes = RouteTable.defaultRouteTable();

    routes.map( "/", StartPage.class );
    routes.map( "/shops/", ShopListPage.class );
    routes.map( "/stats/", StatisticsPage.class );
    routes.map( "/news/*", new NewsRoute() );
    routes.map( "/go/*", new GoRoute() );
}

A pattern is either exact, or a prefix when it ends in *. Routes are tried in the order they're mapped, and the first that answers wins, so put specific patterns before broad ones. A handler can also decline a URL and leave it to the routes after it (see section 5), which is also where you'll find what a URL nothing answers gets. Every routed request is logged with its IP address and user agent, which doubles as a cheap access log during development.

Note that /news/ and /news/* are different patterns: the first is the index, the second everything beneath it. Some applications map a path both with and without its trailing slash so either form works; a two-line helper does that.

The first segment of a path can't be one of the application's request handler keys: wa, wo, res and the like. Those URLs always go to their request handlers, so a route like /wa/report could never be reached, and mapping one throws, naming the key.

2. Four shapes of handler

A handler is anything that turns a RouteInvocation into a WOActionResults: a page, a response, or something that yields one. In practice that means one of four things.

A component class, when the URL simply is a page. The route table instantiates it with the request's context:

routes.map( "/reports/", ReportsPage.class );

A lambda, when there's a decision or a parameter involved. The invocation gives you the parsed URL, the request and its context:

routes.map( "/", ri -> {
    if( ((Session)ri.context().session()).user() != null ) {
        return pageWithName( DashboardPage.class );
    }

    return pageWithName( LoginPage.class );
} );

routes.map( "/articles/*", ri -> {
    final String slug = ri.routeURL().getString( 1 );
    final ArticlePage page = pageWithName( ArticlePage.class, ri.context() );
    page.setArticle( Article.forSlug( slug ) );
    return page;
} );

A method reference, when the handler is more than a few lines. The method takes the invocation and returns the result, and the route table stays a readable list:

routes.map( "/laws", Application::laws );
routes.map( "/laws/*", Application::laws );
routes.map( "/oauth/callback", Application::oauthCallback );

private static WOActionResults laws( final RouteInvocation ri ) {
    final int year = ri.routeURL().getInteger( 1, Year.now().getValue() );
    final Integer article = ri.routeURL().getInteger( 2 );
    final Integer paragraph = ri.routeURL().getInteger( 3 );

    …
}

A class implementing RouteHandler, when the handler carries state or is reused across applications. It's a single-method interface, so a nested static class is all it takes:

routes.map( "/go/*", new GoRoute() );

/**
 * /go/<code> redirects to the shop a short code stands for, counting the click on the way
 */
private static class GoRoute implements RouteHandler {

    @Override
    public WOActionResults handle( final RouteInvocation ri ) {
        final Shop shop = Shop.forShortCode( ri.routeURL().getString( 1 ) );

        if( shop == null ) {
            return DECLINED;
        }

        shop.countVisit();

        final WOResponse response = new WOResponse();
        response.setStatus( 302 );
        response.setHeader( shop.url(), "location" );
        return response;
    }
}

A handler never returns null. When it has no answer for a URL, it returns RouteHandler.DECLINED, as above, and the URL goes on (section 5). A null is taken for a mistake and throws, naming the handler and the URL.

3. Reading parameters

The invocation's routeURL() splits the path on slashes, leading and trailing ones removed, and hands out the pieces by index. Index 0 is the first path element, which for /laws/2026/12 is laws, so parameters start at 1:

final RouteURL url = ri.routeURL();

url.getString( 1 );          // "2026" — or null if the URL is shorter
url.getString( 1, "none" );  // with a default
url.getInteger( 2 );         // 12, as an Integer — or null if it's missing or isn't a number
url.getInteger( 2, 0 );      // with a default, for the same two cases
url.length();                // how many elements the path has

A segment that isn't a number counts as missing, since a URL is whatever the user typed: /laws/abc gets the default, not an exception. When a missing or mistyped number means the URL names nothing, check for null and decline, and the not found handler answers.

Query parameters are not part of the route; the query string is stripped before matching. Read them from the request, as you always have:

routes.map( "/oauth/callback", ri -> {
    final String code = ri.request().stringFormValueForKey( "code" );

    if( code == null ) {
        return badRequest( "Invalid authentication request. Missing code" );
    }

    return finishLogin( code, ri.context() );
} );

This is the shape of an OAuth callback: a fixed path, the interesting part in the query, a decision, a page. Anything on the request is available, ri.request() for headers and form values and ri.context() for the session.

4. What a handler returns

Anything WebObjects can send. Pages are the common case; the rest is WOResponse with the right content and headers:

// A page, with an object set on it
final CompanyPage page = pageWithName( CompanyPage.class, ri.context() );
page.setCompany( company );
return page;

// Data: JSON from a route
routes.map( "/company/*", ri -> {
    final Company company = Company.forName( ri.routeURL().getString( 1 ) );
    final String json = new Gson().toJson( company.balanceSheet() );
    final WOResponse response = new WOResponse();
    response.setHeader( "application/json; charset=utf-8", "content-type" );
    response.setContent( json );
    return response;
} );

// A redirect: 302 on purpose, so browsers don't cache it the way they cache a 301
routes.map( "/login", ri -> {
    final WOResponse response = new WOResponse();
    response.setStatus( 302 );
    response.setHeader( "https://app.example.com/", "location" );
    return response;
} );

Files that browsers and crawlers ask a site's root for, /favicon.ico, /robots.txt, /.well-known/…, don't need a route each: they're public resources (section 5).

5. When nothing answers

Routing is a chain. A URL goes to the routes whose pattern matches it, in the order they're mapped, then to the route table's fallback, if one is set, and then to its not found handler. Each one answers the URL or declines it, and the first answer is the response.

Declining. A handler that returns RouteHandler.DECLINED passes the URL on, to the next route that matches it or to what comes after the routes. So a route can match a pattern and still leave the URL alone: a /* route that answers only the slugs it knows, an object route that declines an identifier that names nothing, a parameter that doesn't parse. Declining is usually better than building a 404 yourself, because the not found handler answers it the same way as every other URL nothing answers, development pages included.

Public resources: the fallback. An application that serves public resources answers the files in the public folder of its web server resources at the root of its URL space: public/favicon.ico at /favicon.ico, public/.well-known/security.txt at /.well-known/security.txt. A URL that isn't one of them goes on to not found. It's off unless the application turns it on:

routes.setFallbackRouteHandler( new ERXPublicResources() );

The fallback comes after every route, so a route always wins over a file.

Not found. The last in the chain, and the one that always answers. Deployed, that's a plain 404 with the URL in the body. In development, wonder-slim sets one that helps instead: an unmapped / shows a welcome page that says what's running and how to map a page of your own, and any other URL gets a 404 page with the URL, the routes that are mapped and how to map one. An application can set its own, a branded 404 page, say, or the plain one in development too, in its constructor:

// A page of your own, answered with the 404 status
routes.setNotFoundRouteHandler( ri -> {
    final WOResponse response = pageWithName( NotFoundPage.class, ri.context() ).generateResponse();
    response.setStatus( 404 );
    return response;
} );

// The plain 404, in development too
routes.setNotFoundRouteHandler( new RouteTable.NotFoundRouteHandler() );

Passing the request on. An application that shares its server with another handler, an ng-objects application in the same Jetty server through wo-adaptor-jetty, has not found decline every URL, so the request is passed on to the next handler in the server:

routes.setNotFoundRouteHandler( new RouteTable.PassOnRouteHandler() );

A URL that every handler in the chain declines is answered with a bare 404 marked unhandled, which wo-adaptor-jetty discards to let the next handler try the request. Nothing else is generated for it, since nobody sees it. Without another handler, leave not found as it is: there's nothing to pass the request on to.

6. The same URLs in development and production

This is the part worth understanding, because it's what makes routes pleasant rather than merely possible.

In development the application listens on its own port, and the URL you type is the URL your handler sees: a request for http://localhost:1200/shops/ lands in the route table as /shops/. There is no adaptor, no rewrite, nothing to configure.

The application's own URLs are short too. Component actions, direct actions and resources are generated without the adaptor prefix, /wo/…, /wa/…, /res/…, and the application accepts them that way. The long form, /cgi-bin/WebObjects/MyApp.woa/wa/…, keeps working, so existing links and bookmarks don't break.

In production behind modulo, a site maps its hostnames to an application, and modulo forwards the request to an instance unchanged. The application sees /shops/ exactly as it did on localhost, so the same handler runs with the same routeURL().

Behind Apache with mod_WebObjects only adaptor URLs reach the application, so a rewrite rule in the virtual host forwards everything else into the application's adaptor URL space, under the route request handler key. With the adaptor at /Apps/WebObjects:

RewriteEngine on
RewriteRule ^/$ /Apps/WebObjects/MyApp.woa/route/ [L,PT]
RewriteCond %{REQUEST_URI} !^/Apps/WebObjects/
RewriteCond %{DOCUMENT_ROOT}%{REQUEST_URI} !-f
RewriteCond %{DOCUMENT_ROOT}%{REQUEST_URI} !-d
RewriteRule ^/(.*)$ /Apps/WebObjects/MyApp.woa/route/$1 [L,PT]

The first rule forwards the root; the second everything else that isn't already an adaptor URL or a file Apache serves itself. The condition on the adaptor path matters: without it, the application's own long URLs would be rewritten a second time. Forwarding under route rather than the bare path matters too: mod_WebObjects reads a number right after .woa as an instance number, so a route like /2026 forwarded bare would never arrive. The route key never appears in a URL anyone sees. The application code is identical; only the front end differs, and the deployment guides show each setup.

7. In practice

  • Keep the table in one place. A Routes class with a static register() method, called from the Application constructor, reads as the site's map. wonder-slim's AjaxPlayground does exactly this.
  • Map the root. / is a route like any other, and it is where the login decision usually lives. Until it's mapped, development shows the welcome page there and production a 404.
  • Prefer flat, stable paths for pages, and reserve wildcards for things with identifiers: /articles/<slug>, /i/<entity>/<id>.
  • Decline what you can't answer. A number that isn't there (or isn't a number) comes back as null from getInteger, and a slug that matches nothing as null from your lookup. Return RouteHandler.DECLINED rather than an error page of your own, and the not found handler answers.
  • Wildcards are prefixes, nothing more. There is no pattern language yet; the matching is deliberately simple, and everything beyond the prefix is yours to parse from routeURL().
  • Request handler URLs come first. /wa/, /wo/, /res/ and the application's other handler keys go to their request handlers before the route table sees anything, even under a catch-all /* route.
  • Describe the current page with RouteRequestHandler.routePath( request ), the path as the routes see it, rather than request.uri(), which carries the form the request arrived in.

The classes are in er.extensions.routes: RouteTable, RouteHandler, RouteInvocation and RouteURL, with ERXPublicResources in er.extensions.resources. The wonder-slim repository has them, and the changelog records how the routing has evolved.
